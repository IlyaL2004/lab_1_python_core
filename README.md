## ЛР2

`pipeline.iter_submissions()` лениво читает JSONL через прежний `JSONLSource` и проверяет записи прежним parser. Совпадающие ID и хеш пропускаются, конфликт содержимого одного ID отклоняется. При переданном списке `errors` ошибки строк накапливаются, а чтение продолжается. В памяти сохраняются ID и хеши, поэтому весь конвейер не имеет постоянного расхода памяти. `file_sha256()` читает файл блоками. При раннем выходе генератор нужно закрывать; пример приведён в API.

В `data/lab2/` зафиксированы **56 сдач, 24 семейства, 132 размеченные пары и 12 пар `template_only`**. Схема `Submission` версии 1 сохранена: происхождение, родители и семейства находятся в `provenance.json`, разбиение — в `split.json`, метки пар — в `pairs.jsonl`. `validate_split()` и `validate_pairs()` проверяют полноту данных, происхождение, отсутствие утечки семейств и допустимость пар. Разбиение задано до сравнения методов. Учебный корпус искусственный; число пар не равно числу независимых наблюдений.

`scripts/build_lab2_corpus.py` документирует создание корпуса и при запуске записывает его файлы. Для обычной проверки пересоздавать данные не требуется. После установки пакета выполните из корня проекта:

```bash
./.venv/Scripts/python.exe -X utf8 -m pytest -q -p no:cacheprovider
./.venv/Scripts/python.exe -X utf8 scripts/check_lab2_corpus.py
```

При активированном окружении вторая команда имеет вид `python -X utf8 scripts/check_lab2_corpus.py`. Она проходит стадии чтения и валидации, выводит JSON в stdout и не перезаписывает прежние результаты. Артефакты проверки этапа сохраняются отдельно в `results/lab2/stage1/`: `tests.txt`, `corpus_check.json`, `verification.json`.

Общая `load_assignments()` перенесена из `cli.py` в `parsing.py`; прежний импорт `school_lab.cli.load_assignments` сохранён. Непарные Unicode-суррогаты отклоняются как ошибка поля, а JSON терминала экранирует символы для совместимости с кодировкой вывода. `source_text.physical_lines()` согласует номера исходных строк анализаторов и evidence: разделители — CRLF, CR и LF; остальные символы внутри строки сохраняются. Содержимое корректных сдач и правила их хеширования не нормализуются.

## Токеновое сравнение

`pipeline.iter_features()` связывает ленивые стадии read → validate → features. Модуль `features.py` извлекает токены через `tokenize`, исключает комментарии и служебные токены, сохраняет имена и литералы. Признаки — множество токеновых 3-грамм. Окна, пересекающие точные строки разрешённого шаблона, исключаются; оставшиеся участки не склеиваются. Синтаксис проверяется через `ast.parse` без выполнения кода; сравнение AST появится отдельно.

`similarity.py` вычисляет Jaccard: размер пересечения делится на размер объединения. Два пустых множества дают `score=null` и `insufficient_data`, одно пустое — 0. Точная копия с непустыми признаками получает 1. При некорректном коде результат содержит `invalid_source`, понятную причину и `score=null`.

Для поиска трёх наиболее похожих работ выполните из корня проекта:

```bash
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli compare data/lab2/submissions.jsonl \
  --assignments data/lab2/assignments.json --method token \
  --query squares-family-0-v0 --top-k 3
```

Без `--query` сравниваются все допустимые пары, а `--output путь.json` дополнительно сохраняет JSON в файл. `--keep-template` включает строки шаблона в признаки. Допустимы только работы разных студентов одного задания; сама работа и другие версии её автора исключаются. Версии остальных студентов остаются отдельными кандидатами. Top-k сортируется по убыванию score, при равенстве — по ID; неопределённые результаты находятся в `undefined_pairs`.

В отчёте пары сохранены ID и хеши исходных версий, метод, версия метода, хеш конфигурации, общие признаки с диапазонами строк обеих работ и исключённые диапазоны шаблона. Проверка отчёта сверяет эти ссылки с оригиналами. `review_required` означает ручной разбор. Порог `--threshold 0.5` пока демонстрационный; настройка по validation и оценка качества относятся к следующей части работы. Даже score=1 не устанавливает авторство или нарушение.

Текущая команда сохраняет проверенные сдачи и результаты в памяти, извлекает признаки заново для каждой пары через `compare_submissions()`. При N работах одного задания получается N(N−1)/2 пар до исключения одинаковых авторов. Память растёт с суммарным размером исходников и числом пар с evidence. Ленивое чтение не делает весь расчёт константным по памяти. API `compare_prepared()` и `top_k()` также принимают уже подготовленные записи; их хранение требует памяти для исходников, признаков и всех вхождений.

Результаты проверки токенового метода сохраняются в `results/lab2/stage2/`. Команды ЛР1 `import` и `analyze` доступны. AST-метод, настройка порогов, оценка качества и измерения производительности добавляются позднее.

## Установка

Нужен Python 3.12 или новее. Команды выполняются из папки проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]" -e ./plugins/declaration
.\.venv\Scripts\python.exe -X utf8 -m pytest -q -p no:cacheprovider
.\.venv\Scripts\python.exe -X utf8 examples/validate_one.py
```

Последняя команда проверяет искусственную запись `data/submission.json` и выводит её поля. При ошибке JSON или схемы она выводит `code`, `field`, `message` и возвращает код завершения 1. Исходный код из поля `code` не исполняется.

Установка `-e` связывает окружение с текущими исходниками. При изменении зависимостей или метаданных повторите установку. Для существующего окружения в Git Bash:

```bash
./.venv/Scripts/python.exe -m pip install -e ".[dev]" -e ./plugins/declaration
./.venv/Scripts/python.exe -X utf8 -m pytest -q -p no:cacheprovider
```

Опция `-p no:cacheprovider` отключает только кеш pytest: она позволяет запускать проверки при ограниченных правах на `.pytest_cache`.

Для полного набора тестов нужен установленный пакет `school-declaration-plugin` из `plugins/declaration`: интеграционные проверки находят его через метаданные установки. Они не пропускаются при отсутствии пакета и не добавляют его исходники в `sys.path`.

Файловые тесты используют фикстуру `temp_dir` из `tests/conftest.py`. Она создаёт отдельную папку через стандартный `tempfile.TemporaryDirectory` и удаляет её после теста, в том числе при ошибке. Общая папка `pytest-of-...`, которая может оказаться недоступной после запуска под другой учётной записью Windows, не используется.

```bash
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli import data/submissions.jsonl
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli import data/invalid_submissions.jsonl
```

После установки также доступна команда `./.venv/Scripts/school-lab.exe import data/submissions.jsonl`.

Первый файл содержит две корректные искусственные сдачи. Его результат:

```json
{"accepted": ["sub-001", "sub-002"], "duplicate": [], "errors": []}
```

Второй файл демонстрирует частичный успех: две сдачи принимаются, одна распознаётся как дубликат, три строки дают ошибки. Строка 2 — повреждённый JSON, строка 4 — конфликт занятого ID, строка 5 — пустой student_id. Последняя корректная запись принимается после этих ошибок.

| Код завершения | Значение |
|---|---|
| 0 | Все записи обработаны без ошибок; допустимы дубликаты |
| 1 | Есть ошибки отдельных строк; корректные записи приняты |
| 2 | Файл недоступен, нарушена UTF-8 кодировка или неверны аргументы CLI |

Результат импорта — один JSON в stdout. Ошибка открытия/чтения файла выводится в stderr. Пустая строка JSONL считается ошибкой формата; номера строк отсчитываются с 1. Блок `with` закрывает файл, включая завершение с исключением.

## Взаимозаменяемые источники

`SubmissionSource` описывает через `Protocol` один общий метод `open()`. В блоке `with` он предоставляет итератор записей `SourceRecord`: номер строки, разобранные данные либо ошибку JSON. `JSONLSource` читает UTF-8 файл построчно, а `InMemorySource` выдаёт словари из памяти. Общая функция `import_source(source, service)` передаёт записи в сервис и собирает прежний `ImportSummary`. Сервис приёма не зависит от способа чтения данных.

Для соответствия `Protocol` достаточно предоставить метод `open()` с нужной сигнатурой; наследоваться от `SubmissionSource` не требуется. При обычном наследовании класс явно указывает базовый класс и может получать его реализацию; протокол здесь описывает только необходимый интерфейс.

`JSONLSource` открывает файл при входе в `with`, а не при создании объекта. Декоратор `contextmanager` позволяет использовать `open()` в блоке `with`; внутренний `with` закрывает файл при выходе из контекста после полного чтения, раннего `break`, исключения или без чтения записей. Ошибки отдельных строк не останавливают импорт; системные ошибки и ошибки UTF-8 передаются вызывающему коду.

Сам `break` завершает только цикл: файл остаётся открыт до выхода из окружающего блока `with`.

Каждый новый вызов `open()` начинает обход с первой записи. `InMemorySource` делает глубокую копию входного списка при создании и отдельную копию каждой выдаваемой записи. Изменение исходного списка или полученного словаря не меняет последующие чтения, включая вложенные данные.

Для уже открытого текстового потока есть `StreamSource(stream)`, например `StreamSource(StringIO(jsonl_text))`. Он читает с текущей позиции и не закрывает поток: владельцем остаётся вызывающий код. Номера записей считаются с 1 от начала текущего обхода. Для повторного чтения переместите поток через `stream.seek(0)`. Поэтому правила повторного чтения и владения ресурсом здесь отличаются от `JSONLSource`.

Для совместимости `import_file(path, service)` осталась: теперь она создаёт `JSONLSource` и вызывает `import_source`. Команда CLI `import` и формат её результата прежние.

Пример сравнения двух источников в Git Bash:

```bash
./.venv/Scripts/python.exe -X utf8 examples/compare_sources.py
```

Пример читает `data/submissions.jsonl` двумя способами. Для каждого источника используется свой репозиторий: первый импорт принимает две сдачи, повторный в тот же репозиторий возвращает два дубликата. Результаты обоих способов совпадают.

## Приём и хранение версий

`SubmissionService.accept(raw)` сначала вызывает parser первого этапа, затем вычисляет SHA-256 и обращается к репозиторию. Для хеша используется JSON всех полей модели с отсортированными ключами, без лишних разделительных пробелов, в UTF-8. Порядок ключей входного словаря не влияет на хеш; исходный текст и код не нормализуются.

| Ситуация | Результат |
|---|---|
| Новый корректный ID | `accepted`, сдача сохраняется |
| Тот же ID и тот же хеш | `duplicate`, возвращаются ID и хеш уже принятой версии |
| Тот же ID с другим содержимым | `SubmissionError` с кодом `conflict`, исходная запись сохраняется |
| Изменённая работа с новым ID | Отдельная принятая версия |

Репозиторий хранит данные только в памяти процесса. Каждый запуск CLI создаёт новое пустое хранилище. Повторный импорт в том же процессе и репозитории проверяется в тестах; два отдельных запуска CLI не имеют общей памяти. Если чтение файла прервалось из-за кодировки или системной ошибки, уже сохранённые записи не откатываются.

## Анализ принятых сдач

Команда `analyze` сначала принимает записи, затем анализирует их в том же процессе. В Git Bash:

```bash
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli analyze data/submissions.jsonl --assignments data/assignments.json
./.venv/Scripts/python.exe -X utf8 examples/analyze_one.py
```

Первый запуск использует анализаторы `length` и `template`. Для двух сдач из примера получается четыре отчёта. В коде `sub-001` находится разрешённая строка шаблона `def add(a, b):`; у `sub-002` такого совпадения нет. Пример `analyze_one.py` показывает создание приложения, приём одной сдачи и запуск этих же двух анализаторов через Python API.

В `data/assignments.json` находится список заданий. У каждого задания есть `assignment_id`, строка `allowed_template` и список строк `requirements`. ID связывает задание со сдачей. Шаблон может быть пустым; требования сохраняются в контексте, но встроенные анализаторы не проверяют произвольный текст требований автоматически. Учебные данные искусственные.

Чтобы выбрать другие анализаторы, повторите `--analyzer`:

```bash
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli analyze data/submissions.jsonl --assignments data/assignments.json --analyzer declaration --analyzer missing-explanation --config-version 2
```

Если передан хотя бы один `--analyzer`, используются только перечисленные имена. `--config-version` по умолчанию равен `1` и входит в хеш конфигурации; пустая или пробельная версия отклоняется как ошибка конфигурации.

| Имя | Наблюдение |
|---|---|
| `length` | Количество непустых строк текста и кода со ссылками на исходные номера строк |
| `template` | Точные совпадения строк кода с разрешённым шаблоном задания |
| `declaration` | Содержимое декларации ИИ; проверка нужна, если помощь заявлена, но студент не отметил проверку результата |
| `missing-explanation` | Наличие кода без текстового пояснения; при его отсутствии требуется проверка |

Анализаторы сохраняют исходную сдачу и формируют наблюдения для преподавателя. Совпадение с разрешённым шаблоном допустимо. Длина кода не определяет правильность решения, а декларация не устанавливает авторство автоматически. Встроенные проверки не вычисляют числовую оценку, поэтому `score=None` превращается в JSON `null`. Флаг `review_required` означает необходимость просмотра, а не автоматическую санкцию.

JSON результата содержит `accepted`, `duplicate`, `errors`, а также `reports`, `analysis_errors` и `measurements`. Анализ выполняется только для ID из `accepted`: повторная строка не создаёт дополнительные отчёты. Ошибка одного анализатора попадает в `analysis_errors`, остальные анализаторы и сдачи продолжают обрабатываться. Если задание для сдачи отсутствует, фиксируется ошибка этой сдачи.

Код завершения 0 означает успешную обработку. Ошибки отдельных строк или анализа дают 1, при этом отчёт остаётся в stdout. Неверная схема файла заданий даёт JSON с кодом `configuration_error` в stderr и завершение 2; недоступный файл или неверная UTF-8 кодировка — `source_unavailable` и 2. Неверные аргументы CLI обрабатывает `argparse` с кодом 2.

## Контракт отчёта и расширение анализа

`AnalysisReport` содержит ID и SHA-256 сдачи, имя и версию анализатора, хеш конфигурации, наблюдения `Finding`, время создания и флаг проверки. `Evidence` ссылается на поле `text` или `code` исходной сдачи: строки считаются с 1, обе границы диапазона включены. Пустые строки не сдвигают ссылки на последующие строки.

`make_report()` создаёт UUID отчёта и время UTC, вычисляет хеши и вызывает `validate_report()`. Проверка отклоняет несоответствие версии сдачи или конфигурации, неправильные диапазоны строк, пустое объяснение и некорректный `score`. Числовой `score` допускается только в диапазоне 0–1 и должен быть конечным; `bool` не подходит. Сдача, задание и наблюдения представлены неизменяемыми моделями.

`AnalysisContext` хранит задание, режим и версию настроек. Изменение задания или настроек меняет `config_hash`. При повторном запуске на тех же данных хеши воспроизводятся, но `report_id` и `created_at` создаются заново.

Контракт `Analyzer` требует `analyzer_id`, `analyzer_version` и синхронный метод `analyze(submission, context) -> AnalysisReport`. `AnalyzerRegistry` связывает имя с фабрикой без аргументов: класс с конструктором без аргументов тоже подходит. `AnalysisService.run()` получает принятую сдачу из репозитория, создаёт выбранный анализатор и проверяет его отчёт. Отсутствие сдачи, неверный контекст, ошибка анализатора или некорректный результат приводят к `AnalysisFailure`.

`build_application()` связывает один репозиторий, сервис приёма, реестр четырёх встроенных анализаторов и сервис анализа. Новый анализатор подключается регистрацией фабрики при сборке приложения:

```python
from school_lab.application import build_application

app = build_application()
app.registry.register("custom", CustomAnalyzer)
report = app.analysis.run(submission_id, "custom", context)
```

Здесь `CustomAnalyzer` — класс с `analyzer_id="custom"`, непустой версией и методом `analyze`. Сдача с `submission_id` должна быть принята, а `context` — соответствовать её заданию. Для подключения не нужно изменять `AnalysisService`. Повторная регистрация имени вызывает ошибку.

## Внешний анализатор

```bash
./.venv/Scripts/python.exe -X utf8 -m school_lab.cli analyze data/submissions.jsonl --assignments data/assignments.json --plugins --analyzer external-declaration
```

Команда создаёт по одному отчёту для каждой принятой сдачи: для примера получится два отчёта. Плагин проверяет заполнение `tool` и `purpose`, когда в декларации указано `used=True`. Parser уже требует эти поля при приёме, поэтому для корректно принятых сдач отчёт документирует полноту декларации. Анализатор демонстрирует расширение отдельным пакетом и не определяет авторство работы.

Флаг `--plugins` разрешает загрузку установленных точек входа группы `school_lab.analyzers`, а `--analyzer` выбирает анализатор для запуска. Если указать только `--plugins`, сохраняется выбор по умолчанию: `length` и `template`. Без `--plugins` внешний анализатор не регистрируется. Команда `import` не загружает плагины. Загрузка импортирует и выполняет код установленного пакета, поэтому подключать следует доверенные плагины.

В Python API загрузка включается через `build_application(plugins=True)`. Функция `load_plugins(registry)` из `school_lab.plugins` обнаруживает точки входа через стандартный `importlib.metadata`, загружает их фабрики и возвращает кортеж зарегистрированных имён в отсортированном порядке. Фабрика создаёт анализатор без аргументов и объявляет `plugin_api_version = 1` — именно `int`, не `bool`. Это версия интерфейса плагина; версия самого анализатора хранится отдельно в `analyzer_version`.

Загрузчик проверяет совместимость интерфейса, уникальность имени и контракт созданного анализатора. Недоступная фабрика, неподдерживаемая версия, совпадение имени со встроенным или другим плагином и неверный контракт вызывают `AnalysisFailure`. В CLI ошибка загрузки даёт `configuration_error` в stderr и код завершения 2. Загрузка не откатывает уже выполненные регистрации: после ошибки нужно создать новый реестр, а не продолжать использовать частично заполненный.



## Измерение времени

Декоратор `timed(measurements)` из `school_lab.timing` записывает длительность синхронного вызова в миллисекундах. Список измерений передаётся извне. Результат функции возвращается без изменений; исключение передаётся вызывающему коду, а измерение всё равно записывается через `finally`. `ParamSpec` и `TypeVar` сохраняют типы параметров и результата, `functools.wraps` — имя, документацию, аннотации и связь с исходной функцией.

```python
from school_lab.timing import Measurement, timed

measurements: list[Measurement] = []

@timed(measurements)
def add(a: int, b: int) -> int:
    return a + b

print(add(2, 3))
print(measurements[0].duration_ms)
```

Команда `analyze` измеряет каждый вызов `AnalysisService.run`, включая ошибочные. В JSON это отдельный список `measurements` с полями `function` и `duration_ms`. Время включает создание анализатора и проверку его отчёта, но не импорт файла и не вывод JSON. Если задание отсутствует, анализатор не запускается и измерение не создаётся. Команда `import` сохраняет прежний формат без измерений.

Время зависит от текущей нагрузки и меняется при каждом запуске. Оно не входит в хеши сдачи и конфигурации; его нельзя использовать как устойчивый идентификатор результата. Декоратор рассчитан на обычные синхронные функции: для генератора или `async def` потребуется другая обёртка.

## Повторение сквозной проверки ЛР1

Сохранённые результаты этого сценария относятся к завершённой ЛР1. Для проверки текущего этапа используйте команды из раздела ЛР2 выше. Если требуется заново получить отчёты ЛР1, после установки обоих пакетов запустите из корня проекта в Git Bash:

```bash
./.venv/Scripts/python.exe -X utf8 -m pytest -q -p no:cacheprovider
./.venv/Scripts/python.exe -X utf8 scripts/verify.py
```

Скрипт повторяет импорт в один репозиторий, проверяет распознавание дубликатов и запускает четыре встроенных анализатора и установленный `external-declaration`. Каждый отчёт проходит обычную проверку сервисом анализа. Скрипт создаёт `results/reports.json` с отчётами и `results/verification.json` с итогами, хешами файлов данных и измерениями времени. Повторный запуск обновляет эти два файла. UUID, время создания отчётов и длительности изменяются; хеши одинакового входа и конфигурации воспроизводятся. Результат полного запуска pytest сохранён в `results/tests.txt`; проверка установки пакетов в чистое окружение — в `results/installation.json`.

## Что проверяется

- Обязательные поля присутствуют, неизвестных полей нет.
- Версия схемы — целое число 1; `True` и строка `"1"` не допускаются.
- Идентификаторы — непустые строки.
- Время задано в ISO-формате с часовым поясом.
- Хотя бы одно из полей `text` и `code` непустое после проверки пробелов.
- `used` и `verified_by_student` — настоящие `bool`.
- При `used=True` указаны непустые `tool` и `purpose`.
- Повторяющиеся ключи JSON и константы NaN/Infinity отклоняются.

Пробелы и переводы строк исходника сохраняются. Parser создаёт новую модель и не меняет входной словарь. Обычное присваивание полям модели и вложенной декларации запрещено через `frozen=True`; сама аннотация типа ничего не проверяет во время выполнения.
