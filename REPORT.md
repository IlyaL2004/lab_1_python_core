# Лабораторная работа 1 — приём работ и расширяемые анализаторы

Траектория — **Python Core**, основной и углублённый варианты. 

## Цель и исходные материалы

Разработать основу системы, которая принимает версии студенческих работ, проверяет данные и запускает заменяемые анализаторы. В работе используются модели `dataclass`, структурные контракты `Protocol`, композиция, исключения, контекстные менеджеры и упаковка Python-проектов.

Основа реализации — `Лекция.ipynb` и задание `ЛР_1_Приём_и_расширяемость.pdf`. Прикладной код использует стандартную библиотеку Python. Тесты написаны на `pytest`, как в лекции. Для основного варианта Python Core ручная проверка схемы реализована без Pydantic.

В проекте подготовлены две искусственные сдачи в `data/submissions.jsonl`, отдельная запись для простого примера и смешанный файл с повторами и ошибками. `data/assignments.json` содержит разрешённый шаблон и требования. Это демонстрационные данные проекта, а не полный корпус лекции. Исходный код в поле `code` обрабатывается как текст и не исполняется.

## Архитектура

Порядок обработки: **источник → разбор JSON → проверка схемы → сервис приёма → репозиторий → анализатор → проверенный отчёт**.

| Компонент | Ответственность |
|---|---|
| `models.py` | Неизменяемые модели сдачи, задания и результата анализа |
| `parsing.py` | Разбор JSON, проверка полей и типов |
| `hashing.py` | Канонический JSON и устойчивый SHA-256 |
| `repositories.py` | Контракт хранилища и реализация на словаре |
| `sources.py` | Чтение JSONL, записей из памяти и внешнего потока, общий импорт |
| `services.py` | Приём, реестр фабрик и запуск анализа |
| `reports.py`, `analyzers.py` | Контракт отчёта, его проверка и встроенные наблюдения |
| `application.py` | Связывание репозитория, сервисов и реестра |
| `plugins.py` | Обнаружение установленных внешних анализаторов |
| `timing.py` | Измерение длительности вызова без изменения результата |
| `cli.py` | Аргументы команд, вывод JSON и коды завершения |

Зависимости передаются явно через конструкторы и `build_application()`. Общего изменяемого хранилища нет. Сервис приёма не открывает файлы, а сервис анализа не перечисляет конкретные классы анализаторов. Поэтому источник, репозиторий или анализатор можно заменить отдельно.

`Protocol` описывает методы и атрибуты подходящего объекта. Явное наследование от протокола не требуется. Обычное наследование задаёт иерархию классов и может передавать реализацию; в этой работе зависимости преимущественно связываются композицией. Аннотации типов помогают описать контракт, но входные JSON и результаты расширений проверяются во время выполнения отдельно.

## Этап А: приём и валидация

`Submission` и вложенная `AIDeclaration` объявлены как `dataclass(frozen=True, slots=True)`. Parser создаёт новые объекты и сохраняет исходные строки без обрезания пробелов. Изменение входного словаря после приёма не меняет сохранённую работу.

Проверяются точный набор полей, версия схемы 1, типы, непустые идентификаторы, ISO-время с часовым поясом и наличие текста либо кода. Для логических полей разрешён именно `bool`; значение `True` не принимается вместо целочисленной версии. При заявленном использовании ИИ обязательны инструмент и цель. Повторные ключи JSON и NaN/Infinity отклоняются.

Ошибки имеют поля `code`, `field`, `message`. Импортёр добавляет физический номер строки с 1 и продолжает работу после ошибки отдельной записи. Различаются неправильный JSON, ошибка схемы, неподдерживаемая версия и конфликт ID. Пустая строка JSONL считается ошибочной записью.

SHA-256 вычисляется от канонического JSON всех полей сдачи: ключи отсортированы, разделительные пробелы убраны, используется UTF-8. Порядок ключей входного словаря не влияет на результат. Текст, код и запись времени сохраняются в исходном виде. Встроенный `hash()` не подходит для постоянного отпечатка между процессами.

| Вход | Результат |
|---|---|
| Корректная работа с новым ID | `accepted`, запись сохраняется |
| Тот же ID и тот же хеш | `duplicate`, сохраняется прежний объект |
| Тот же ID с изменёнными данными | `conflict`, прежняя запись не перезаписывается |
| Изменённая работа с новым ID | Принимается отдельная версия |

`Acceptance` возвращает статус, ID и хеш принятой версии. Репозиторий хранит данные в памяти процесса. Поэтому повторный импорт проверяется в одном приложении; два отдельных запуска CLI создают два независимых хранилища.

## Этап Б: источники и анализаторы

`JSONLSource` и `InMemorySource` соответствуют `SubmissionSource.open()`. Внутри `with` они выдают итератор `SourceRecord`. Общая функция `import_source()` передаёт записи сервису. Повторное открытие обоих источников начинает обход с первой записи.

Файловый источник читает строки по мере обхода. Дескриптор принадлежит контекстному менеджеру и закрывается при выходе из `with`, включая исключение, раннее прекращение цикла или отсутствие чтения. Сам `break` выходит только из цикла: файл остаётся открыт до выхода из контекста. Источник из памяти делает глубокую копию входа и каждой выдаваемой записи, включая вложенную декларацию.

Дополнительный `StreamSource` выполняет упражнение с `io.StringIO`: он читает переданный текстовый поток с текущей позиции, а владелец потока отвечает за его закрытие. Выход из контекста завершает только итератор. Для повторного чтения вызывающий код выполняет `seek(0)`, если поток поддерживает перемотку. Этот источник соответствует общему интерфейсу, но имеет другие правила владения и повторного чтения.

`Analyzer` требует имя, версию и метод `analyze(submission, context)`. Реестр хранит фабрики без аргументов. Для нового класса достаточно регистрации фабрики: сервис анализа менять не нужно.

| Анализатор | Смысл результата |
|---|---|
| `length` | Количество непустых строк с указанием исходных номеров |
| `template` | Точные совпадения строк кода с разрешённым шаблоном |
| `declaration` | Сведения о декларации; отметка для просмотра, если результат ИИ не проверен студентом |
| `missing-explanation` | Отметка для просмотра, если код есть, а пояснения нет |
| `external-declaration` | Полнота инструмента и цели использования ИИ через отдельный пакет |

Совпадение с разрешённым шаблоном допустимо. Длина не доказывает правильность программы, а декларация не устанавливает авторство. Поэтому встроенные наблюдения используют `score=None`. Флаг `review_required` означает необходимость просмотра преподавателем.

`AnalysisReport` содержит ID отчёта и сдачи, SHA-256 сдачи, имя и версию анализатора, хеш конфигурации, наблюдения, время создания и флаг просмотра. `Evidence` указывает поле `text` или `code` и включительный диапазон исходных строк с 1. Пустые строки участвуют в нумерации.

Сервис проверяет результат анализатора: совпадение ID, хеша сдачи и конфигурации, типы, допустимые диапазоны строк и непустые объяснения. Числовая оценка допускается только в пределах 0–1; `bool`, NaN и бесконечность отклоняются. Исключение анализатора становится `AnalysisFailure`; CLI сохраняет его в `analysis_errors` и продолжает остальные проверки.

Конфигурация включает задание, режим и версию настроек. Их изменение меняет `config_hash`. На одинаковом входе воспроизводятся хеши и содержательные наблюдения, но UUID отчётов и время создания формируются заново.

## Углубление: внешний пакет

`plugins/declaration` — отдельный устанавливаемый пакет `school-declaration-plugin` версии 1.0.0. Он объявляет `external-declaration` в группе entry points `school_lab.analyzers`. Загрузчик использует `importlib.metadata`, проверяет версию интерфейса `plugin_api_version=1`, имя и контракт фабрики, затем регистрирует её.

Флаг `--plugins` разрешает загрузку установленных расширений. Выбор самого анализатора задаётся через `--analyzer external-declaration`. Без этого выбора по умолчанию запускаются `length` и `template`. Импорт сдач не загружает плагины.

Тесты проверяют реальный установленный пакет и его точку входа, а также несовместимость версии API, повтор имени, ошибку импорта и нарушения контракта. Исходники внешнего пакета не подставляются в `sys.path`. После неудачной загрузки нельзя продолжать работу с частично заполненным реестром: приложение нужно собрать заново.

Плагин повторяет проверку полноты декларации, уже выполненную parser при приёме. Его назначение — показать подключение независимого пакета и сформировать отдельное объяснение без изменения сервиса анализа.

## Углубление: декоратор времени

`timed(measurements)` принимает список результатов и возвращает декоратор. `ParamSpec` сохраняет типы параметров, `TypeVar` — тип результата. `functools.wraps` сохраняет метаданные и ссылку `__wrapped__`. Длительность считается через `perf_counter` и добавляется в список в блоке `finally`.

Обёртка возвращает тот же результат или передаёт исходное исключение. Ошибочный вызов тоже получает измерение. Список передаётся извне, поэтому глобального накопителя нет. Тесты проверяют передачу аргументов, результат, исключение, метаданные и видимую сигнатуру.

CLI измеряет вызовы `AnalysisService.run`: создание анализатора, сам анализ и проверку отчёта. Время файлового импорта и записи JSON в эти измерения не входит. Результаты находятся отдельно в `measurements`, не меняя контракт `AnalysisReport` и его хеши. Если задание не найдено, вызов анализа не производится и измерение не записывается.

Декоратор добавляет чтения таймера и запись в список; эти накладные расходы отдельно не измеряются. Длительность зависит от нагрузки и среды. Для генераторов и асинхронных функций нужна другая обёртка: эта реализация предназначена для обычных синхронных вызовов.

## Проверка и воспроизводимость

Установка и повторная проверка в Git Bash из папки проекта:

```bash
./.venv/Scripts/python.exe -m pip install --upgrade ".[dev]" ./plugins/declaration
./.venv/Scripts/python.exe -X utf8 -m pytest -q -p no:cacheprovider
./.venv/Scripts/python.exe -X utf8 scripts/verify.py
```

Функциональные тесты проверяют схему, неизменяемость, устойчивые хеши, дубликаты и конфликты, совместимость источников, закрытие файлов, отчёты, реестр, CLI, установленный плагин и декоратор. Для файловых тестов используется `TemporaryDirectory`; общий каталог `pytest-of-...` не нужен. Отключение кеша pytest не отключает проверки.

| Упражнение лекции | Реализация и проверка |
|---|---|
| 1. Ошибки вложенных полей и типов | Parser отклоняет отсутствующее поле декларации, строку `"false"` и пустой `template_id`, возвращая код и поле ошибки; отдельно проверяется неизменность входа |
| 2. Новая версия работы | Новый ID сохраняет обе версии, занятый ID с изменённым кодом вызывает конфликт |
| 3. Отсутствие пояснения | `MissingExplanationAnalyzer` регистрируется общей фабрикой и проходит контрактные проверки |
| 4. Разрешённый шаблон | Точное сопоставление последовательности строк, ссылки на исходные диапазоны, различие пробелов и повторные совпадения |
| 5. Источник из `StringIO` | `StreamSource`; поток закрывает и перематывает вызывающий код |
| 6. Некорректный отчёт | Отклоняются неверная оценка, несуществующее поле и недопустимые номера строк |
| 7. Изменение конфигурации | Замена `config_version` или шаблона меняет хеш; прежний отчёт не подходит новому контексту |

Проверка выполнена на Windows с Python 3.13.9. Установлены `school-lab` и `school-declaration-plugin` версии 1.0.0. Результат полного набора: **215 тестов прошли за 2,62 с**; вывод сохранён в [results/tests.txt](results/tests.txt).

Сквозной сценарий `scripts/verify.py` выполнил два импорта одного файла в одно приложение. Получены 2 `accepted` при первом импорте и 2 `duplicate` при втором. Пять анализаторов создали 10 отчётов без ошибок анализа и 10 измерений. Отдельное приложение проверило смешанный файл: 2 принятые сдачи, 1 дубликат и 3 ошибки на строках 2, 4, 5; после ошибок принята последняя корректная запись.

| Измерение контрольного запуска | Значение |
|---|---:|
| Количество вызовов `AnalysisService.run` | 10 |
| Суммарная длительность | 1,1869 мс |
| Средняя длительность вызова | 0,11869 мс |

Это один локальный запуск, а не сравнительный тест производительности. Скрипт суммирует `duration_ms` всех вызовов и делит сумму на их количество. Измерения показывают работу декоратора; они не доказывают ускорение программы и меняются при повторном запуске.

В [results/reports.json](results/reports.json) находятся отчёты, а в [results/verification.json](results/verification.json) — результаты сценария, хеши, сведения о среде и фактическое время каждого вызова. Повторная проверка обновляет эти файлы. Хеши позволяют сопоставить результаты с данными и настройками; случайные ID, время создания и длительности при повторении меняются.

Оба пакета также собраны в wheel и установлены без сети в новое чистое виртуальное окружение. Проверки запускались из каталога вне проекта, без `PYTHONPATH`; модули загружались из `site-packages`. Импорт через CLI принял две сдачи и вернул 0. Команда `school-lab.exe` обнаружила внешний анализатор через entry points и создала два отчёта и два измерения с кодом 0. `pip check` не обнаружил проблем зависимостей. Фактические результаты сохранены в [results/installation.json](results/installation.json).

## Пояснения для защиты

1. **Где проверяются типы?** Во внешнем JSON — parser; в ответе анализатора — проверка отчёта. Аннотации не выполняют эти проверки автоматически.
2. **Почему нужна глубокая копия?** Поверхностная копия словаря оставляет общую вложенную декларацию. Глубокая копия изолирует её изменения.
3. **Что обеспечивает frozen?** Запрет обычного присваивания полям. Вложенный изменяемый список мог бы меняться, поэтому доменные модели используют неизменяемые значения и кортежи.
4. **Кто закрывает файл после break?** Контекстный менеджер `JSONLSource` при выходе из окружающего `with`. Переданный в `StreamSource` поток закрывает вызывающий код.
5. **Что значит повторяемый результат?** Одинаковые хеши и наблюдения при одинаковых входах; UUID, даты и измеренное время могут отличаться.
6. **Как добавить анализатор?** Зарегистрировать фабрику либо установить пакет с подходящей точкой входа и включить плагины.
7. **Что сохраняет декоратор?** Аргументы, результат, исключение и метаданные функции. Измерение записывается дополнительно в отдельный список.
8. **Какие ошибки видит пользователь CLI?** Ошибки строк и анализа попадают в JSON в stdout с кодом завершения 1. Проблемы чтения и конфигурации дают JSON в stderr и код 2. Неверные аргументы показывает `argparse`; успешная обработка возвращает 0.

## Ограничения

Хранилище существует только в памяти; база данных, конкурентный приём и откат уже принятых строк при системной ошибке не реализованы. Файл читается построчно, но сдачи, итоги и измерения накапливаются в памяти. Внешние плагины работают в процессе приложения и должны быть доверенными. Минимальная версия в метаданных — Python 3.12; фактически проверена 3.13.9, отдельный запуск на 3.12 не выполнялся.

Анализ синхронный. Правильность алгоритмов, авторство и плагиат автоматически не устанавливаются. Произвольный текст требований задания хранится в контексте, но не интерпретируется анализаторами. Данные демонстрационные, а не реальные работы студентов. Документация входов и выходов находится в [docs/API.md](docs/API.md), сведения об использовании ИИ — в [AI_USAGE.md](AI_USAGE.md).
